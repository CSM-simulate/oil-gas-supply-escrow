# Смарт контракт эскроу для поставки нефти и газа

Готовый учебный проект по заданию `SmartContract.docx`: покупатель создаёт и оплачивает партию, поставщик отмечает доставку, покупатель подтверждает приёмку либо отклоняет партию. Если поставки нет к дедлайну, покупатель возвращает оплату. Контракт, тесты, скрипты и документация подготовлены с помощью GPT.

Для запуска распакуйте архив проекта либо склонируйте репозиторий по его URL. Откройте терминал в каталоге с `package.json`.

## Проверенный результат

Проверка выполнена 11 октября 2026 года. Финальная версия компилируется Solidity 0.8.28; **84 теста проходят**. Развёртывание и демонстрация выполнены в локальной сети Hardhat с chainId 31337. Slither 0.11.3 не сообщил проблем уровня High или Medium; четыре Low-предупреждения о timestamp и одно Informational о низкоуровневом переводе разобраны в [audit-notes.md](audit-notes.md).

В первом черновике обнаружена и исправлена ошибка: `markDelivered` позволяла позднюю доставку, блокирующую возврат по сроку. Фактический вывод двух упавших тестов сохранён отдельно от успешного итогового прогона.

## Установка и запуск

Нужны Node.js 22 или 24, npm и Git. Проверенная среда: Node.js 24.19.0, Hardhat 2.28.0, ethers 6.15.0, OpenZeppelin Contracts 5.4.0. Все зависимости зафиксированы в `package-lock.json`. Запускайте команды из каталога проекта, где находится `package.json`.

```sh
npm ci
npm run compile
npm test
npm run deploy
npm run demo
```

`npm ci` требует интернет для первой установки. Далее компилятор solc-js берётся из локального npm-пакета `solc@0.8.28`; скачивание отдельного компилятора Hardhat не требуется. Настройки: оптимизация 200 проходов, EVM Paris.

`npm run deploy` разворачивает контракт в одноразовой локальной сети Hardhat и выводит адрес, участников и хэш транзакции. После завершения процесса эта сеть исчезает. По умолчанию deployer — аккаунт 0, buyer — аккаунт 1, supplier — аккаунт 2 из локальных тестовых аккаунтов. В демонстрации buyer и supplier — аккаунты 0 и 1, поскольку отдельный deployer для неё не нужен.

Для сети, остающейся доступной между командами, откройте два терминала:

```sh
# Терминал 1
npm run node

# Терминал 2
npm run deploy:local
```

Чтобы задать собственные адреса участников в PowerShell:

```powershell
$env:BUYER_ADDRESS="0x..."       # настоящий Ethereum-адрес покупателя
$env:SUPPLIER_ADDRESS="0x..."    # другой настоящий адрес поставщика
npm run deploy:local
```

Для локальной демонстрации ключи, кошелёк и реальные ETH не нужны. Подключение публичной сети в проекте не настроено; все приложенные артефакты относятся к локальным запускам.

## Архитектура и роли

Контракт `OilGasEscrow` использует OpenZeppelin `AccessControl` и `ReentrancyGuard`. Buyer и supplier задаются конструктором и остаются неизменяемыми. Никому не выдан `DEFAULT_ADMIN_ROLE`, смена участников невозможна. Отказ от роли запрещён, чтобы случайное действие не блокировало оплату. Посторонние адреса могут читать данные и события.

Партия содержит все поля задания: `id`, `volume`, `priceWei`, `specHash`, `status`, `deadline`. Объём выражается целым числом в единице, согласованной в спецификации. Цена — в wei, где 1 ETH = 10^18 wei. `specHash` — keccak256 точных байтов согласованного документа; `deadline` — Unix timestamp в секундах. Метаданные согласуются сторонами вне блокчейна, а покупатель фиксирует их при создании заказа согласно заданной сигнатуре `createBatch`. Поставщик не может менять уже оплаченные условия.

| Функция | Участник | Назначение |
|---|---|---|
| createBatch(id, volume, priceWei, specHash, deadline) | buyer | Создать заказ |
| fundBatch(id), payable | buyer | Внести ровно priceWei до deadline |
| markDelivered(id) | supplier | Отметить доставку до deadline |
| releasePayment(id) | buyer | Принять Delivered и перечислить цену supplier |
| refund(id) | buyer | Вернуть цену Funded при timestamp >= deadline |
| rejectBatch(id, reasonHash) | buyer | Отклонить Delivered и сразу вернуть цену |
| getBatch(id), batchExists(id) | любой | Прочитать сведения |
| buyer(), supplier(), totalEscrowed(), hasRole(...) | любой | Проверить участников и учёт |

Статусы имеют значения: Created = 0, Funded = 1, Delivered = 2, Released = 3, Refunded = 4.

```text
Created -> Funded -> Delivered -> Released
              |           |
              |           +-> Refunded  (отклонение покупателем)
              +-------------> Refunded  (нет доставки к дедлайну)
```

Своевременной считается доставка при `block.timestamp < deadline`. На точной границе возврат уже доступен, доставка и оплата запрещены. После своевременной доставки истечение срока не отменяет её: покупатель выбирает приёмку или отклонение. `refund` не возвращает Delivered-партию автоматически. Для возврата по несоответствию используется дополнительная функция `rejectBatch`; она покрывает отклонение из общего сценария задания, сохраняя требуемые пять статусов.

`releasePayment` доступна покупателю, поскольку его вызов и есть подтверждение получения и соответствия спецификации. Поставщик не может единолично разрешить себе выплату. События: `BatchCreated`, `Funded`, `Delivered`, `PaymentReleased`, `Refunded`, дополнительное `BatchRejected`.

## Безопасность и тесты

Денежные функции, включая отклонение с возвратом, защищены `nonReentrant`. Для выплат действует Checks-Effects-Interactions: сначала проверяются роль и статус, затем меняются статус и `totalEscrowed`, после этого выполняется перевод. Ошибка получателя откатывает всю транзакцию; повторная попытка возможна без потери средств.

Тесты проверяют успешную поставку, возврат по сроку, отклонение, все недопустимые переходы, отсутствие прав, неверные суммы, повторные выплаты и финансирование, неизвестные и повторные ID, границы срока −1/0/+1 секунда, отказ ETH-получателя и повторный вход. Учёт проверяется на разных ценах, смешанных исходах и воспроизводимой последовательности из 32 партий. Отдельный тест моделирует принудительное поступление ETH.

Основной инвариант: `totalEscrowed` равен сумме `priceWei` партий в Funded и Delivered. Баланс должен быть не меньше этой суммы: принудительно поступившие ETH не относятся к оплате партий. Для обычных потоков тесты проверяют равенство. Вспомогательные контракты из `contracts/test/` используются только тестами, скрипт deploy их не разворачивает. Предупреждение компилятора о `selfdestruct` относится исключительно к `ForceEther`, моделирующему принудительный перевод, и отсутствует в основном контракте.

### Воспроизведение статического анализа

Дополнительно нужны Python 3.12 и Slither. На Windows зафиксирован полный набор пакетов в `docs/requirements-audit.txt`:

```sh
python -m venv .venv
# Активировать .venv: Windows PowerShell — .\.venv\Scripts\Activate.ps1
# Linux/macOS — source .venv/bin/activate
python -m pip install -r docs/requirements-audit.txt
```

На Linux/macOS вместо Windows-набора зависимостей установите `python -m pip install slither-analyzer==0.11.3`.

```sh
npx hardhat clean
npm run compile
python -m slither . --compile-force-framework hardhat --hardhat-ignore-compile --filter-paths "node_modules|contracts/test|contracts\\test" --exclude-dependencies --fail-medium
```

`--fail-medium` возвращает ошибку при проблемах Medium/High, сохраняя в выводе Low/Informational. Отсутствие ошибки не означает отсутствие замечаний. Старые результаты компиляции очищаются, чтобы в анализ не попали предыдущие версии контракта. После очистки при необходимости повторите `npm test`.

## Ограничения

Контракт не измеряет физический объём и качество, не проверяет сертификаты и не разрешает споры. Покупатель оценивает поставку вне блокчейна; `specHash` и `reasonHash` связывают решения с документами. Покупатель может затянуть решение по Delivered-партии; дополнительный срок приёмки и независимый арбитраж в базовую модель не входят. Потеря ключей и получатель, постоянно отказывающийся от ETH, могут заблокировать средства. Принудительно присланные сверх оплаты ETH остаются на контракте без функции изъятия. Учебный мини-аудит не заменяет независимую проверку перед использованием реальных средств.
